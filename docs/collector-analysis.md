# Движок сбора: разбор узких мест · 09.09.2026

Продукт стоит на движке сбора. Всё остальное — экраны, отчёты, медианы —
описывает то, что движок принёс; если он приносит неполное или
искажённое, безупречная аналитика поверх этого лишь аккуратно показывает
неправду. Поэтому движок разбирается первым и правится раньше остальных
частей бэклога.

Разбор сделан по коду и по живым данным: 8700 вакансий в базе, 92 файла
сборов в `data/raw`, история запусков. Каждая находка — с числом, которое
можно перепроверить, а не с ощущением.

## Как устроен сбор сейчас

```
config.yaml (58 запросов)
    │
    ▼
VacancyCollector._collect_by_keyword(запрос)
    │   страницы по 100, до max_pages = 10
    │   для страниц 0–1 и только для новых вакансий — карточка (детали)
    ▼
normalize.normalize_vacancy()
    │   навыки ищутся словарём по тексту: snippet.requirement,
    │   snippet.responsibility, description, name
    ▼
storage.save_vacancies_incremental()  → upsert по vacancy_id
```

Отдельно живёт `src/processor.py` (`VacancyProcessor`) — прежний путь
обработки. В цепочке сбора он не участвует: коллектор импортирует
`normalize`. Два пути расходятся в важном (см. § 1).

---

## 1. Навыки, названные источником, не используются вовсе

**Что происходит.** hh.ru отдаёт `key_skills` — список навыков, который
работодатель заполнил руками в отдельном поле. Это лучший источник
навыков, какой бывает: не догадка по тексту, а прямое утверждение.

В живом пути (`normalize.searchable_text`) собираются
`snippet.requirement`, `snippet.responsibility`, `description` и `name`.
Поля `key_skills` там нет. Слово `key_skills` не встречается ни в
`normalize.py`, ни в `collector.py`, ни в `storage.py`.

Старый `processor.py` его хотя бы склеивал в общий текст — но и там
навык проходил через словарь, то есть выживал, только если мы его уже
знали.

**Сколько теряется.** По трём последним файлам сборов (1022 вакансии):

| | |
|---|---|
| упоминаний навыков от источника | 1147 |
| из них нет в нашем словаре | 886 (77 %) |
| уникальных навыков от источника | 477 |
| из них теряется | 402 |

Среди потерянных: 1С-Битрикс, Adobe Photoshop, 3ds Max, amoCRM, Ahrefs,
A/B тесты, ABC-анализ, Allure. Это не экзотика — это ровно те навыки,
ради которых человек и приходит смотреть рынок.

**Почему так вышло.** Словарь навыков в `config.yaml` писался руками под
ИТ-рынок: 926 позиций. Всё, что вне его, для продукта не существует.
Рынок при этом шире словаря на порядок и меняется быстрее, чем словарь
успевают дописывать.

## 2. Детали берутся у 43 % вакансий, и это видно по числу навыков

**Что происходит.** Карточка вакансии — отдельный запрос на каждую
вакансию, поэтому она берётся только для первых двух страниц каждого
запроса (`DETAILED_PAGES = 2`, то есть до 200 вакансий) и только для
новых. Остальные приходят из поисковой выдачи, где есть лишь короткая
выжимка.

**Что это даёт на живых данных** (8700 вакансий):

| | |
|---|---|
| с деталями | 3775 (43 %) |
| навыков в среднем с деталями | 7,7 |
| навыков в среднем без деталей | 1,8 |
| вакансий вообще без навыков | 1638 (19 %) |
| без hard_skills | 43 % |
| без tools | 71 % |

Разрыв вчетверо. Пятая часть базы участвует в аналитике навыков нулём —
и не потому, что навыков нет в вакансии, а потому, что мы не спросили.

## 3. Извлечение навыков: было 36 мс, стало 3,5 мс

Словарь применялся как отдельное регулярное выражение на каждый навык:
цикл по словарю, `re.search` на каждом. Первый замер дал 36 мс на
вакансию — час на сто тысяч записей.

### Что сделано (09.09.2026, группа S3)

К моменту, когда до этого дошли руки, число уже было другим: проверка
обычным вхождением подстроки перед каждой регуляркой (её добавили в
S9) сбила расход до 6,8 мс. Замер на живых описаниях, а не на
синтетическом тексте — 1079 навыков, средняя длина описания 2 260
символов.

**Отсев по словам вместо тысячи проходов.** Текст разбивается на слова
один раз; у каждого навыка заранее посчитано множество его слов. Навык,
ни одно слово которого в тексте не встречается, не может быть найден
ни одним из способов — ни целиком, ни по частям, ни вариантом
написания, ни через начальную форму. Пересечение двух множеств стоит
доли миллисекунды и отбрасывает девять десятых словаря: до
сопоставления доходят 107 навыков из 1079.

| | На вакансию | На 100 000 вакансий |
|---|---|---|
| первый замер (S9) | 36 мс | 1 час |
| до отсева | 6,8 мс | 11 минут |
| после отсева | 3,5 мс | 6 минут |

**Якорь считается не только по названию.** Первая версия отсева брала
слова самого навыка — и на пятистах описаниях потеряла навыки в 111
случаях. «Аукционы» находятся в тексте «аукционах» через начальную
форму, «Next.js» — через вариант написания «nextjs», и слов названия
там нет. Теперь в якорь входят название, начальная форма и все
варианты; леммы текста участвуют в отсеве наравне с самим текстом.

**Проверено на равенство, а не на глазок.** Новый поиск сверен со
старым на 1000 живых описаний: расхождений ноль. Это и было условием —
ускорение не имеет права менять, какие навыки попадают в базу.

**Автомат (Aho–Corasick) не понадобился.** Он дал бы тот же порядок
величины, но потребовал бы зависимости и переписывания всех четырёх
способов поиска. Дальнейшее ускорение — замена проверки частей на
проверку по множеству слов — отвергнуто сознательно: токенайзер
разбивает «node.js» на «node» и «js», а регулярка с границами слова
там совпадения не даёт, и поведение бы разошлось.

Теперь главная статья расхода — не словарь, а морфология: приведение
текста к начальным формам стоит 5,9 мс против 3,5 мс на поиск.

## 4. Одна вакансия, размноженная по городам, считается многими

Работодатель размещает одну вакансию в десятках городов; у каждой копии
свой `vacancy_id`, и для базы это разные записи.

| | |
|---|---|
| строк в базе | 8700 |
| уникальных `vacancy_id` | 8700 |
| пар «название + компания», встречающихся ≥ 2 раз | 355 |
| строк в таких парах | 1079 (12 %) |

Рекорды: «Сотрудник ресторана ROSTIC S» — 31 копия, «Рекрутер в сервис
доставки САМОКАТ» — 28, «AI-тренер для обучения нейросетей» (Яндекс
Крауд) — 24.

Дедупликация по `vacancy_id` этого не ловит и не должна: копии
действительно разные записи источника. Но в медиане зарплат, в топе
работодателей и в счёте «вакансий в месяц» одна вакансия весит как
тридцать.

Это не однозначный дефект: для среза «сколько предложений в городе N»
копии считать надо. Нужен явный выбор — и он должен быть виден на
экране, а не спрятан в коде.

## 5. Полнота выдачи ничем не гарантирована

- `max_pages = 10`, `per_page = 100` → потолок 1000 вакансий на запрос.
- Источник по популярному запросу отдаёт десятки тысяч; сверх потолка мы
  не видим ничего и не говорим об этом.
- hh.ru сам ограничивает выдачу 2000 результатами на запрос — глубже не
  пройти в принципе, даже подняв `max_pages`.
- Регион в запрос не передаётся (задача 2.4.1): выборка перекошена в
  сторону крупных городов, и это единственный доступный способ обойти
  потолок в 2000 — резать запрос по регионам и датам.

Признак `complete` у запроса есть и честно запрещает гасить пропавшие
вакансии при неполном обходе — это сделано правильно. Но «выдача
прочитана не до конца» нигде не превращается в число, которое видит
человек: сколько мы недобрали, он не знает.

### Что сделано (09.09.2026)

**Недобор стал числом.** По каждому запросу теперь записывается не
только «найдено», но и «взято» — сколько записей выдачи мы прочитали
(колонка `taken`, миграция 014). Разница между ними и есть то, чего мы
не увидели. Она считается только по неполным обходам: у полного разрыв
объясняется отсевом по возрасту, и называть его потерей — враньё.
На экране «Сбор данных» это одна фраза: «2 412 вакансий осталось за
пределом выдачи по 1 запросу… Больше всего по запросу «Prompt
Engineer»: источник знает 3 412, прочитано 1 000».

**Регион уходит в запрос.** Замер живыми запросами 09.09.2026:

| Запрос | Найдено |
|---|---|
| «Рекрутер» без региона | 10 294 |
| «Рекрутер», Москва (1) | 2 043 |
| «Рекрутер», Санкт-Петербург (2) | 645 |

Предел источника — 2000 на запрос, и он подтверждён его же ответом:
`pages = 20` при сотне на странице, сколько бы ни было «найдено». То
есть по «Рекрутеру» мы видели пятую часть.

**Запрос режется на срезы.** Если найдено больше, чем источник вообще
отдаёт, читать такой запрос вглубь бессмысленно — он оборвётся на
двухтысячной вакансии. Вместо этого тот же запрос обходится по частям:
страны верхнего уровня, а страна, которая сама упёрлась, — по своим
регионам, и так вглубь до срезов, помещающихся в выдачу. Лист дерева,
упёршийся всё равно, честно уходит в недобор.

Три решения, которые здесь приняты:

- **Корни резки — страны, а не регионы России.** В базе есть вакансии
  в тенге, сумах и лари; сузив резку до российских областей, мы
  потеряли бы остальные страны так же тихо, как раньше теряли всё за
  пределом выдачи.
- **Ключ кэша учитывает срез.** Раньше в него входили только запрос,
  страница и размер страницы: «Рекрутер» по Москве и по всей стране
  читались из одной ячейки. Резка на таком кэше молча возвращала бы
  одни и те же вакансии.
- **Резка выключена по умолчанию** (`SPLIT_BY_REGION`). Она превращает
  один запрос к источнику в десятки и меняет длительность сбора в разы.
  Такой выбор делает человек, зная цену; бюджет срезов `MAX_SLICES`
  ограничивает обход даже при включённой резке.

**Замер на живом запросе** («Рекрутер», 30 дней, 10 страниц на срез,
бюджет 12 срезов, 09.09.2026):

| | Взято | Уникальных | Время |
|---|---|---|---|
| без резки | 1 000 | 1 000 | 0,9 мин |
| со срезами | 4 447 | 4 167 | 7,2 мин |

4 447 — вдвое больше жёсткого предела источника в 2 000. Цена честная:
семь минут вместо одной по одному запросу.

**Порядок обхода решает, что достанется.** Первый замер дал всего 1 114
вакансий: срезы шли в порядке справочника — Марий Эл, Татарстан,
Удмуртия, Чувашия, — и бюджет кончался, не дойдя до Москвы. Теперь
перед обходом каждый срез взвешивается одним лёгким запросом (страница
из одной вакансии, из ответа берётся только «найдено»), и обход идёт от
крупных к мелким. Те же двенадцать срезов дали вчетверо больше.

## 6. Что не выстрелило, но выстрелит

**Схема источника меняется молча.** Поля читаются напрямую
(`vacancy.get("salary_range")`, `snippet.requirement`). Если hh
переименует поле или изменит формат, сбор не упадёт — он тихо начнёт
писать пустоту. Ровно так уже случилось с периодом выплаты: поле
`salary_range.mode` существовало, а продукт его не читал, и часовые
ставки лежали рядом с месячными окладами.

**Прогресс сбора живёт в памяти процесса.** Перезапуск приложения
посреди сбора — и продолжить нечем: начинать заново. При сборе на
десятки тысяч вакансий это часы работы.

**Бюджет запросов не считается.** Сколько запросов уйдёт на сбор,
заранее неизвестно; ограничение частоты обрабатывается реактивно (429 →
пауза → повтор). Для одного источника хватает, для нескольких — нет.

**Кэш ответов с зашитым сроком.** `ttl_hours=24` стоит в вызове `set()`;
задача 2.9 это признаёт. Кэш не различает «выдача поиска» и «карточка
вакансии», хотя устаревают они по-разному.

**Мёртвый путь обработки.** `src/processor.py` не участвует в сборе, но
жив, экспортирует `VacancyProcessor` и содержит свою логику навыков.
Следующая правка навыков может уйти не туда — та же ловушка, что была со
старыми анализаторами отчёта (C1-7).

### Что сделано (09.09.2026, группа S6)

**Схема источника проверяется контрактом.** `src/contract.py` называет
минимум, без которого запись бесполезна: идентификатор, название,
работодатель, дата публикации, регион — и описание у карточки. Проверка
идёт на первой странице каждого запроса: схема меняется у источника
целиком, а не у отдельной вакансии. Нарушение не роняет сбор — вакансия
без описания всё равно даёт название и зарплату, — но пишется в журнал
ошибкой и считается в статистике. Отдельно замечается переезд полей:
пропажа и `salary`, и `salary_range` сразу — это предупреждение, а не
поломка, потому что вакансия без зарплаты бывает.

Тесты идут по настоящим ответам hh.ru, сохранённым в
`tests/fixtures/ответ_поиска.json` и `ответ_карточки.json`: проверять
контракт на выдуманных словарях значило бы проверять свою же фантазию.

**Прогресс переехал в базу.** Колонка `progress_state` (миграция 016)
хранит, какие запросы пройдены целиком. Перезапуск приложения посреди
сбора больше не значит «начинать заново»: следующий запуск пропускает
пройденные запросы — их вакансии уже в базе.

Продолжается только то, что оборвалось само (статус `interrupted`).
Сбор, остановленный человеком, продолжать нельзя: он сказал «хватит», и
молча дособрать за него — сделать не то, о чём просили. Набор запросов
должен совпадать, а сам обрыв быть не старше суток: дальше выдача
источника успевает смениться, и «продолжение» мешало бы сегодняшнее со
вчерашним.

**Качество сбора стало числом.** После каждого запуска в историю
пишутся три числа (миграция 015): сколько записей получили карточку,
сколько не дали ни одного навыка, сколько запросов прочитаны не до
конца. Считаются они по записям этого запуска, а не по базе: качество
базы меняется медленно и прячет ухудшение сегодняшнего сбора. На экране
«Сбор данных» — колонка «С карточкой» с долей в процентах и подсказкой
с числами; у сборов до миграции стоит прочерк, потому что «не измеряли»
и «ноль» — разные вещи.

**Бюджет сбора считается заранее.** Экран обещал «около минуты» на
запрос — по полминуты за каждый. Живые сборы из истории: 1 411 вакансий
за 18 минут, 1 141 за 23 минуты. Теперь цена считается на сервере
(`src/budget.py`) из числа страниц, числа карточек и паузы между
запросами, и показывается вилкой: «4 запроса · от 4 до 39 мин». Нижняя
граница — повторный сбор, где карточки известных вакансий не нужны;
верхняя — первый. Одно число значило бы выбрать, в какую сторону
соврать. Оба живых сбора попадают внутрь вилки — это и проверяется
тестом.

**Частота уже подстраивалась** под отказы источника: при 429 задержка
удваивается с потолком и возвращается к базовой после серии успехов
(`src/api_client.py`, тесты в `test_api_client_limits.py`).

## 6а. Словарь навыков стал данными (09.09.2026, группа S7)

**Словарь переехал из конфига.** 1158 позиций лежали в `config.yaml`
рядом с поисковыми запросами и параметрами обработки: данные, которые
меняются еженедельно, — в файле, который правят раз в полгода. Теперь
это `data/skills.yaml`. При переносе убрано 78 повторов: почти все —
одна и та же позиция сразу в двух разделах, вроде «Docker» в hard и в
tools.

**Появились синонимы.** Работодатели пишут одно и то же по-разному, и
для продукта это были разные навыки. Живой счёт по базе:

| Как писали | Упоминаний |
|---|---|
| 3ds Max / 3D Max / 3dmax / 3DsMax / 3D-max | 131 + 90 + 1 + 1 + 1 |
| JavaScript / Java Script | 103 + 2 |
| VueJS / Vue.js | 12 + 9 |
| Битрикс24 / Битрикс 24 | 44 + 4 |

В топе навыков «3ds Max» и «3D Max» стояли двумя строками, деля между
собой 221 упоминание, — каждая была занижена вдвое.

**Почему список, а не правило.** Напрашивается нормализация: убрать
пробелы, дефисы и регистр — и написания сольются сами. В тех же данных
лежит опровержение: у **«C#» и «C++» такой «скелет» совпадает**.
Автоматика свела бы два разных языка в один. Поэтому таблица синонимов
составлена руками по всем 47 группам похожих написаний из базы, а
«скелет» служит только тем, чтобы подсказать кандидатов.

По той же причине в таблицу не вошли «AI agents» и «AI-агент»: это
перевод, а не написание. Английское сводится к английскому, русское — к
русскому.

**Что изменилось в базе.** Скрипт `канон_навыков.py` привёл к канону
2 514 записей: 477 × «3Ds Max» → «3ds Max», 442 × «Chatgpt» → «ChatGPT»,
344 × «Bitrix24» → «Битрикс24», 203 × «Javascript» → «JavaScript».
Уникальных навыков у активных вакансий стало 1 960 вместо прежних
россыпей одного и того же.

**Ловушка, найденная по дороге.** Напрашивалось применить канон
пересчётом по файлам сборов — скрипт для этого уже есть. Сухой прогон
показал: навыков стало бы меньше на 9 543, и первым в списке потерь
шёл «Подбор персонала» (452 упоминания). Причина — в файлах сборов
`key_skills` есть только у 6 562 записей из 22 710, а в базе навыки
работодателя проставлены у 7 400: разницу восстановил скрипт
обогащения из более поздних сборов. Пересчёт стёр бы её молча.

Теперь `пересчёт_навыков.py` считает убыль и останавливается, если она
больше десятой части, требуя явного `--согласен-на-убыль`. А канон
применяет отдельный скрипт, который только переименовывает: ни одна
запись не пересчитывается, ни один навык не исчезает.

**`str.title()` дробил статистику наравне с разнописанием.** Навык из
словаря показывался через `skill.title()` — заглавная буква у каждого
слова. Это ломало двумя способами сразу, и оба стояли в топе дашборда:

| Как показывалось | Как надо |
|---|---|
| Llm 232 · Rag 201 · Crm 176 · Api 166 · Ml 106 · Sql 91 | LLM, RAG, CRM, API, ML, SQL |
| Оценка Персонала 237 **+** Оценка персонала 154 | Оценка персонала 391 |
| Адаптация Персонала 208 **+** Адаптация персонала 164 | Адаптация персонала 372 |

Второй случай хуже первого: словарный «Оценка Персонала» и названный
работодателем «Оценка персонала» — это один навык, посчитанный дважды,
и каждая половина занижена вдвое.

Правильное написание известно только там, где его записал человек, —
в таблице синонимов; туда внесены 63 аббревиатуры и CamelCase-названия
(«LLM», «CI/CD», «PostgreSQL», «TypeScript»). Всё остальное получает
заглавную первую букву, а внутри фразы понижаются только слова из
чистой кириллицы вида «Ххххх» и одиночные предлоги: «Внимательность К
Деталям» → «Внимательность к деталям». Латиница не трогается вовсе —
«MS Office», «Power BI», «Adobe Photoshop» и «1С» работодатель пишет
сам, и знать лучше него мы не можем.

В базе это 4 899 записей: 862 × «Crm» → «CRM», 802 × «Llm» → «LLM»,
589 × «Грамотная Речь» → «Грамотная речь». Уникальных навыков у
активных вакансий стало 1 878 вместо 1 960 — разница и есть тот же
навык, прежде посчитанный дважды.

**Мёртвый путь обработки дал о себе знать.** После переезда словаря
`src/processor.py` стал получать ноль навыков: он читал `config.yaml`
напрямую. Чинилось это одной строкой — чтение через `skills_store`, —
но подтвердило опасение из § 6: у мёртвого кода своя логика навыков, и
она расходится с живой молча. Заодно убраны `HARD_SKILLS`, `SOFT_SKILLS`
и `TOOLS` из `config.py` — снимки словаря на момент импорта, которыми
никто не пользовался и которые замкнули импорт в круг.

## 7. Чего нет по сравнению с обычной практикой сборщиков

Приёмы, которые в системах такого рода считаются стандартом. Взяты не
«для полноты», а под конкретные дыры выше.

| Приём | Зачем здесь |
|---|---|
| **Возобновляемый обход (чекпойнт)** | состояние запроса и страницы в базе, а не в памяти: сбор продолжается после перезапуска |
| **Очередь задач вместо цикла** | запрос — единица работы со своим статусом; повтор упавшего не требует повтора всего сбора |
| **Резка запроса по срезам** | обход потолка выдачи: тот же запрос по регионам и по датам публикации |
| **Бюджет и адаптивная частота** | планируемое число запросов и скорость, подстраивающаяся под 429, а не только реагирующая |
| **Контракт ответа источника** | явная схема полей с проверкой: сбор кричит при изменении формата, а не пишет пустоту |
| **Фикстуры реальных ответов** | тесты на сохранённых ответах источника — единственный способ поймать смену схемы до боевого сбора |
| **Метрики качества сбора** | доля с деталями, доля без навыков, доля неполных обходов — как показатели, а не как разовые проверки |
| **Словарь навыков как данные** | пополняемый из `key_skills` источника, с версией и историей, а не список в `config.yaml` |
| **Нормализация сущностей** | работодатель и регион приводятся к канону: «Самокат» и «САМОКАТ (ИП …)» — одна компания |
| **Идемпотентность повторного разбора** | повторная обработка того же файла даёт тот же результат — иначе backfill опасен |

## 8. Путь к другим источникам

Сейчас движок сросся с hh.ru: имена полей источника попадают прямо в
нормализацию, клиент знает про `HH-User-Agent` и про формат `area`,
`salary_range`, `snippet`. Добавить второй источник (РФ, Китай, Европа)
значит либо скопировать всё, либо разорвать связку.

Разрыв проходит по трём местам:

1. **Клиент источника** — общий интерфейс: поиск по запросу с
   пагинацией, карточка по идентификатору, свои правила частоты и
   авторизации. Дальше — по классу на источник.
2. **Приведение к общей записи** — у каждого источника свой переводчик в
   единые поля продукта. Общего у них ровно то, что уже есть в таблице:
   название, компания, регион, зарплата с валютой и периодом, навыки,
   даты.
3. **Идентичность записи** — `vacancy_id` перестаёт быть уникальным
   между источниками; ключом становится пара «источник + внешний
   идентификатор». Это миграция таблицы, и делать её надо до того, как
   появится второй источник, а не после.

Валюты и период выплаты уже сделаны правильно и переносятся без
изменений: курс ЦБ, `salary_mode`, правило «не складывать разные
валюты». Это готовый фундамент для международных источников.

---

### Что сделано (09.09.2026, группа S8)

Все три места разорваны.

**Клиент источника стал контрактом.** `src/sources/контракт.py`
описывает, что движок вправе спросить: искать, брать карточку, называть
свои регионы. `src/sources/hh.py` — первая реализация, а не «главная».

**Имена полей hh.ru не выходят за свой слой.** `alternate_url`,
`key_skills`, `snippet.requirement`, `salary_range.mode` живут теперь
только в переводчике; нормализация работает с общими полями —
«название», «работодатель», «валюта», «период», «текст». Проверено
вымышленным вторым источником, у которого поля называются `title`,
`company`, `pay`: он проходит общий код без единой правки в нём, и
навыки у него находятся так же.

Чего в общем контракте нет намеренно: полей, которые есть только у hh —
рейтинга работодателя, меток «срочно», внутренних кодов регионов. Общий
контракт — это пересечение того, что умеют все источники, а не
объединение; частное живёт в слое своего источника.

**Ключ записи — пара «источник + идентификатор»** (миграция 017).
Идентификаторы у сайтов свои: «137176862» на одном не имеет отношения к
«137176862» на другом, и прежний уникальный индекс объявил бы их одной
вакансией — одна затёрла бы другую молча, без ошибки и следа в логах.
Миграция сделана на 8 700 записях одного источника, все они достоверно
принадлежат hh.ru; чем позже, тем дороже она обходится.

По дороге нашлась ошибка в собственной правке: счётчик новых записей
считал по одним идентификаторам, и две вакансии с одинаковым номером с
разных сайтов давали «вставлена одна». Теперь счёт идёт по парам.

**Источник виден на экране — но только когда их несколько.** Фильтр
«Источник» и подпись у строки появляются со вторым источником: пока
сайт один, «Все источники» — выбор без выбора, а подпись «hh.ru» у
каждой строки повторяет одно и то же. Проверено на копии базы с двумя
источниками на 390 / 768 / 1440.

**Правила денег не привязаны к источнику.** Валюта и период выплаты
берутся из его данных, а не подставляются: у вакансии с неназванной
валютой в базе стоит пустое значение, а не рубль. Подставить рубль
значило бы положить чужие деньги в рублёвую статистику.

## 10. Извлечение навыков из текста: что замерено и какие есть способы

Работодатель заполняет `key_skills` не всегда и не полностью, а в тексте
описания навыков обычно больше. Ниже — замеры на 2189 вакансиях из
`data/raw` и разбор способов извлечения.

### 10.1. Текст и `key_skills` дополняют друг друга, а не заменяют

| | |
|---|---|
| вакансий с полным описанием | 57 % (медиана 2367 символов) |
| вакансий с `key_skills` | 38 % |
| с описанием, но **без** `key_skills` | 416 из 2189 |
| навыков из `key_skills`, **отсутствующих в тексте** | 59 % |

Последняя строка — главная. Больше половины навыков, которые
работодатель назвал в отдельном поле, в тексте не упомянуты вовсе:
`HTML5`, `MongoDB`, `Selenium`, `Django Framework`, `CI/CD`. И наоборот:
у 416 вакансий текст есть, а поля нет. Значит нужны оба источника, и ни
один не отменяет другой.

### 10.2. Словарь находит 64 % того, что заведомо есть в тексте

Проверка на 400 вакансиях: берём навыки из `key_skills`, оставляем те,
что буквально присутствуют в тексте (эталон — 1328 упоминаний), и
смотрим, сколько из них найдёт нынешний словарь.

**Нашёл 849 из 1328 (64 %).** Причины пропусков — три, и они разные:

1. **Дыр в словаре.** `HTML`, `CSS`, `API`, `UML`, `BPMN`, `HTTP`,
   `SOAP`, `Redux`, `Node.js`, `CSS3`, `HTML5` в нём просто нет. Словарь
   писался под Python/ML-стек и не догнал остальной рынок.
2. **Порог длины.** `MIN_SKILL_LENGTH = 3` выбрасывает `Go`, `C#`, `R`,
   `UX`, `QA`, `ML`, `BI`, `JS` — они есть в конфиге, но до поиска не
   доходят. Порог поставлен правильно по причине (иначе `R` находится в
   каждом слове), но лечит симптом слишком широким жестом.
3. **Спецсимволы.** `C#`, `Node.js`, `C++` не ловятся `\b`-границами:
   `#`, `.` и `+` не буквы, и граница слова работает не там, где ожидается.

### 10.3. Где искать важнее, чем чем искать

Описания hh структурированы: 1800 выделенных подзаголовков на 300
вакансий. Самые частые — «Условия» (93), «Обязанности» (81),
«Требования» (77), «Мы предлагаем» (30), «Будет плюсом» (23).

Поиск сейчас идёт по всему тексту разом. Что из этого выходит на 215
вакансиях с секциями:

| Где найдено | Навыков |
|---|---|
| «Требования», «Обязанности», «Задачи» | 513 |
| «Условия», «Мы предлагаем» | 62 |

Вторая строка — чистый шум, и он уже виден на экране. В живой базе:

| «Навык» | Вакансий |
|---|---|
| Развитие | 260 |
| Мотивация | 129 |
| Подарки | 70 |
| Зарплата | 49 |
| Больничные | 26 |
| Корпоративы | 14 |

**«Подарки» стоят в топ-10 навыков на дашборде.** Это корпоративные
подарки из раздела условий, засчитанные как профессиональный навык.
Разделение текста на секции убирает этот класс ошибок целиком — и стоит
дешевле любого улучшения самого поиска.

### 10.4. Способы извлечения: что чего стоит

**А. Словарь по подстроке (сейчас).** Предсказуем, объясним, быстр после
починки скорости (S3), не требует ничего внешнего. Знает ровно то, что в
него записали. Годится как основа, но не как единственный слой.

**Б. Секции текста.** Не способ извлечения, а сужение области поиска.
Самый выгодный шаг из всех: убирает 12 % ложных навыков, ничего не теряя
и ничего не усложняя. Делать первым.

**В. Морфология (`pymorphy3` уже в зависимостях).** Приводит русские
формы к начальной: «управлял проектами» → «управление проектами».
Помогает на русских составных навыках, бесполезна для английских
терминов — а их в ИТ-выдаче большинство. Узкий, но дешёвый выигрыш.

**Г. Автопополнение словаря из данных.** `key_skills` источника — готовый
поток эталонных названий (S1, S7). Плюс частотные n-граммы из текстов
как кандидаты: то, что часто встречается рядом с известными навыками,
скорее всего навык. Кандидаты не попадают в словарь сами — они попадают
в очередь на подтверждение. Это то, что делает словарь живым, не
превращая его в свалку.

**Д. Модель распознавания сущностей (NER).** Обученная модель находит
навыки, которых нет ни в каком словаре, и понимает контекст. Цена:
размеченный корпус (сотни вакансий руками), вес модели в поставке,
скорость на порядок ниже словаря и недетерминированность — один и тот же
текст в разных версиях модели даёт разный результат. Для продукта, где
числа должны воспроизводиться, это существенный минус. Разумно как
второй проход по тем вакансиям, где словарь нашёл мало.

**Е. Разбор языковой моделью (LLM).** Даёт лучшее качество: понимает
«писал на го» и «опыт с постгресом», нормализует написания, отличает
требование от условия. Цена: деньги и время на вакансию,
недетерминированность, отправка текста наружу. Практический вид — не
онлайн, а офлайн-проход: батчем, с кэшем по хэшу текста, только для
вакансий, где остальные слои дали мало. И главное — как **источник
кандидатов для словаря**, а не как замена ему: тогда результат
воспроизводим, а модель работает один раз на текст, а не при каждом
показе.

### 10.5. Без эталона улучшать нельзя

Все шаги выше меняют числа на экранах. Сейчас нет способа сказать, стало
лучше или хуже: «нашли больше навыков» не значит «нашли правильно» —
«Подарки» тоже прибавка.

Нужен золотой набор: 200–300 вакансий с руками размеченными навыками,
разных рынков (ИТ, рабочие профессии, HR, услуги). По нему считаются два
числа — полнота (сколько настоящих навыков нашли) и точность (сколько
найденного оказалось навыком). Каждое изменение сравнивается с
предыдущим замером, и регресс виден до того, как попадёт на экран.

Замер из § 10.2 — черновая замена такому набору: `key_skills`,
присутствующие в тексте, дают приближённый эталон полноты бесплатно. Он
неполон (не покрывает навыки, которых нет в `key_skills`), но им можно
пользоваться, пока размеченного набора нет.

### 10.6. Порядок

1. **Секции** (§ 10.3) — убирает ложные навыки, ничего не ломая.
2. **Починка словаря**: дыры, порог длины, спецсимволы (§ 10.2) —
   с 64 % полноты до заметно большего без единой новой технологии.
3. **`key_skills` как источник** (S1) и автопополнение словаря (S7).
4. **Эталонный набор и метрики** (§ 10.5) — до того, как трогать
   что-то умное.
5. **Морфология** — узкий выигрыш на русских формулировках.
6. **LLM-проход как поставщик кандидатов** — когда есть чем измерить
   результат.
7. **NER** — только если после всего этого останется разрыв, который
   нечем закрыть.

### 11.1. Восемь способов назвать навык

**Тип 1. Стек списком.** Плотный перечень через запятую.

> «Стек проектов: Python, asyncio, FastAPI, Django; PostgreSQL и
> SQLAlchemy; docker, gitlab, k8s»

Самый простой случай, и именно на нём словарь работает лучше всего.

**Тип 2. Навык с раскрытием уровня.** Родительский навык, за которым
идут подробности владения.

> «React: функциональные компоненты, хуки (useState, useEffect, useMemo,
> useCallback, useContext, кастомные хуки), работа с формами (React Hook
> Form)»
> «Figma (компоненты, варианты, Auto Layout, интерактивные прототипы)»

Сейчас берётся только родитель — «React», «Figma». Подробности, по
которым и отличается middle от junior, теряются целиком.

**Тип 3. Навык внутри действия.** Инструмент назван по ходу описания
задачи, а не в списке требований.

> «Внедрение и настройка воронки продаж в CRM-системе (Битрикс24 /
> amoCRM), интеграция телефонии»
> «Постановка задач подрядчикам по трафику (Яндекс.Директ, Авито,
> соцсети) и контроль стоимости лида (CPL/CPA)»

Это вакансия коммерческого директора: в `key_skills` у неё восемь общих
формулировок («Управление продажами», «B2B Продажи»), а вся конкретика —
Битрикс24, amoCRM, Яндекс.Директ, Авито, CPL/CPA, Trade-in, Росреестр,
ИЖС — только в тексте.

**Тип 4. Отраслевые аббревиатуры.** Вне ИТ-словаря их нет вовсе.

> «автоматизация складов (WMS, WCS), транспортная логистика (TMS, YMS),
> цифровизация производства (MES), автоматизация производства (АСУ ТП)»
> «Базовое понимание терминов affiliate-маркетинга (CTR, CR, ROI)»

**Тип 5. Профессиональные методы.** Не инструменты, а приёмы ремесла.

> «Использование современных инструментов сорсинга (Boolean search и
> др.), проведение телефонных интервью (первичный скрининг)»
> «тест-анализ», «груминг бэклога», «дизайн-ревью», «шахматки с этапами
> повышения цен»

**Тип 6. Требования, которые не навыки.** Их надо уметь отличать.

> «Высшее профильное образование», «опыт от 3 лет», «полностью
> заполненное резюме», «Во время конкурса желательно не использовать
> инструменты ИИ»

**Тип 7. Поисковый хвост.** У массовых вакансий в конце идёт набитый
список запросов.

> «сборка заказов, подработка с ежедневными выплатами, работа для
> начинающих, работа по совместительству, гибкий график, работа у дома,
> свободный график, разнорабочий, оплата сразу, утреннее, дневное,
> вечернее, время, режим, ночная работа, работа без опыта»

Это не навыки и не условия — это ключевые слова для поиска. Любое
извлечение, идущее по всему тексту, будет их подбирать.

**Тип 8. Языки и уровни.** Почти всегда только в тексте.

> «Отличные коммуникативные навыки на русском и английском языках»

### 11.2. Что из этого видит продукт сегодня

Три примера, посчитанные на тех же вакансиях.

**Backend Developer (Python/FastAPI), `key_skills` пусто.** Словарь нашёл
15 навыков — неплохо. Пропустил: `NATS`, `WebSocket`, `FastStream`,
`Dishka`, `Dependency Injection`, `Netmiko`, `Paramiko`, `AsyncSSH`,
`pysnmp`, `TCP/IP`, `ООП`, `паттерны проектирования`, `Unix`. Примерно
половина.

**Middle Front-end.** `key_skills`: Scrum, TypeScript, React, Git,
JavaScript. Словарь нашёл четыре, из них один — «Зарплата». Пропустил
`Framer Motion`, `TanStack Query`, `Zustand`, `Storybook`, `Playwright`,
`ES6` — то есть ровно то, чем эта вакансия отличается от сотни других
фронтендерских.

**Сорсер (подбор персонала), `key_skills` пусто.** Словарь нашёл **один**
навык: «Взаимодействие». Не найдены `Boolean search`, `сорсинг`,
`скрининг`, `LinkedIn`, `hh.kz`, `CRM`, `база кандидатов`. Вакансия
рекрутера для продукта, который собирает рынок рекрутинга, оказалась
практически невидимой.

### 11.3. Ложные срабатывания: не просто шум, а подмена смысла

Проверка контекста найденного показала, откуда берутся странные навыки:

| Записано как навык | Откуда в тексте |
|---|---|
| `Access` (Microsoft Access) | «jwt (**access**/refresh tokens)» |
| `Контроль` | «**контроль** версий: git» |
| `Зарплата` | «**зарплата** обсуждается индивидуально» |
| `Высшее Образование` | «**высшее** профильное **образование**» |

В той же вакансии не найдены `JWT`, `OAuth2`, `RBAC`, `Joi`, `Zod`,
`Git Flow`, `rebase`. То есть словарь одновременно теряет настоящее и
придумывает несуществующее — и второе опаснее: «Access» в статистике
инструментов выглядит как факт о рынке.

### 11.4. Что отсюда следует

1. **`key_skills` и текст — разные по природе.** Поле содержит
   обобщённые компетенции («Управление продажами», «Product
   Management»), текст — конкретные инструменты и методы (amoCRM,
   Boolean search, TanStack Query). Продукту нужны оба слоя, и путать их
   нельзя: по первому строится карта профессий, по второму — карта
   инструментов.
2. **Чем дальше от ИТ, тем важнее текст.** У ИТ-вакансий `key_skills`
   заполняют часто и по делу; у продаж, HR, маркетинга и рабочих
   профессий поле либо пустое, либо состоит из общих слов, а всё
   существенное — в описании.
3. **Границы навыка важнее списка навыков.** Половина ошибок — не
   «нет в словаре», а «найдено не то»: обрезанное «контроль» вместо
   «контроль версий», `access` из чужого термина. Извлечение по
   отдельным словам без контекста будет ошибаться всегда.
4. **Иерархия навыков реальна.** «React → хуки → useCallback» и
   «Figma → Auto Layout» — это не три навыка в куче, а уровни владения
   одним. Плоский список их не выражает.

## 12. Может ли продукт понимать текст, а не следовать скрипту

Короткий ответ: да, и это правильный ход — но не как замена нынешнему
движку, а как слой над ним, с жёстко очерченными полномочиями.

### 12.1. Что именно должна делать модель

**Извлечение навыков из текста.** Ровно то, где словарь бессилен:
`Boolean search`, `FastStream`, `WMS`, «шахматки», «хуки React» — модель
берёт их из смысла, а не из совпадения строк. Она же отличает
`access/refresh tokens` от Microsoft Access, а «контроль версий» от
«контроля».

**Сведение к канону.** `3ds Max` / `3dmax` / `3д макс` — одно.
`Постгрес` / `PostgreSQL` / `Postgres` — одно. Сегодня это три разные
строки в статистике.

**Разметка ролей текста.** Что здесь требование, что обязанность, что
условие, а что поисковый хвост. Это дешевле правил и надёжнее: у
половины вакансий подзаголовков нет вовсе.

**Планирование сбора.** Самая «агентная» часть: по тому, что уже есть в
базе, решать, каких запросов и регионов не хватает, где выборка тонкая,
какой профессии в справочнике не соответствует ни одна вакансия — и
предлагать следующий сбор. Сейчас это делает человек, глядя на конфиг.

### 12.2. Чего модель делать не должна

**Писать числа в аналитику напрямую.** Продукт спорит со средней
зарплатой ради воспроизводимости: одна и та же база должна давать одну и
ту же медиану. Модель недетерминированна — один текст в двух прогонах
даёт разные списки. Если её ответ идёт сразу в базу, числа начинают
плыть без единой новой вакансии, и объяснить это будет нечем.

**Решать в момент показа.** Экран должен строиться на готовых данных.
Модель работает при обогащении — один раз на текст, с сохранением
результата.

**Оставаться без следа.** Каждый навык, извлечённый моделью, должен
нести версию модели и промпта. Иначе через полгода нельзя будет
объяснить, почему цифры за март не сходятся с сегодняшним пересчётом.

### 12.3. Как это устроить

```
сбор → сырой текст
         │
         ├─ детерминированный слой: key_skills, словарь, секции
         │      (быстро, воспроизводимо, объясняет каждый навык)
         │
         └─ слой понимания (LLM), офлайн, с кэшем по хэшу текста
                │
                ├─ навыки с пометкой «извлечено моделью» + версия
                └─ кандидаты в словарь → подтверждение → словарь растёт
```

Ключевое — вторая стрелка снизу. **Модель не только извлекает, но и
учит словарь.** То, что она нашла дважды и трижды, становится обычной
позицией словаря, и в следующий раз находится детерминированно и
бесплатно. Со временем доля текстов, где модель вообще нужна, падает —
она работает по краю нового, а не по всему потоку.

Для чего это критично: **при переходе на другие источники** (Китай,
Европа) словарь придётся собирать заново под каждый рынок и язык.
Модель, которая пополняет словарь сама, — единственный способ сделать
это без ручного труда на каждый источник.

### 12.4. Чем платим

| Цена | Величина и что с ней делать |
|---|---|
| Деньги | описание — 500–2000 токенов; на 100 000 вакансий это заметная сумма. Гасится кэшем по хэшу текста и тем, что модель зовут только для вакансий, где остальные слои дали мало |
| Время | секунды на вакансию против миллисекунд у словаря. Поэтому только офлайн, батчем, вне пути показа |
| Невоспроизводимость | лечится фиксацией версии модели и температуры, кэшем и тем, что результат модели превращается в словарь, а не остаётся её личным мнением |
| Приватность | описания вакансий публичны, персональных данных в них нет — риск низкий, но выбор модели (внешняя или локальная) должен быть осознанным |
| Дрейф качества | новая версия модели меняет ответы. Лечится эталонным набором из § 10.5: перед сменой модели прогоняется замер |

### 12.5. С чего начинать

Не с агента. С измеримой задачи на одном узком месте:

1. Эталонный набор (§ 10.5) — без него любое «стало лучше» недоказуемо.
2. Модель на 200–300 вакансиях, где словарь нашёл меньше трёх навыков, —
   там от неё максимальная польза и минимальная цена.
3. Сравнение с эталоном: полнота и точность против словаря.
4. Если выигрыш подтвердился — режим пополнения словаря, а не прямой
   записи.
5. И только потом — планирование сбора, где модель решает, что собирать
   дальше.
